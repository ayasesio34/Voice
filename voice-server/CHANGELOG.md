## 1.9.0

### 子频道（服务端部分）

`channels` 表加 `parent_id TEXT` ✓（NULL = 顶层 ✓）走 migrate() 给老库补 ✓

规则**三条**（缺一不可 ✓）—— 用户明确选的是"只一层、同类"：

1. 父频道必须存在 ✓ → `parent_not_found`
2. 父频道和自己必须**同类** ✗ → `parent_kind_mismatch`
3. 父频道自己**必须是顶层** ✗ → `nest_too_deep`

**⚠️ 第 3 条是唯一一处"必须"在服务端拦的地方** ✗
界面上可以只列顶层频道当候选项 ✓ 但那是"不给入口"✓ 不是权限控制 ✓
构造一条带深层 parentId 的请求照样能发过来 ✓

### ⚠️⚠️ 最值得记的一个坑：老库上**外键根本不存在** ✗

表定义里写了：

```sql
parent_id TEXT REFERENCES channels(id) ON DELETE CASCADE
```

但那只对**新建的库**有效 ✗
老库的 `parent_id` 是 `migrate()` 里 `ALTER TABLE` 加上来的 ✓
而 **SQLite 不支持用 ALTER 加外键** ✗

→ 老库上删父频道时**一点级联都不会发生** ✓
→ 留下一堆子频道 ✓ 它们出现在列表里、点进去是个空壳 ✓
→ **而且再也删不掉了**（父频道已经没了 ✓ 而只有父频道的右键菜单里才有"删除频道"）✗

所以 `deleteChannel()` **自己显式删子频道** ✓ 新旧库行为一致 ✓

**→ 测试里专门手工造了一个老式 `channels` 表** ✓
   （只有老的那几列 ✓ 没有 parent_id、没有外键 ✓）
   让服务端自己 migrate() ✓ 然后再验一遍连坐 ✓
   这才是真的在测"升级上来的库" ✓ 而不是"刚建好的库" ✗

### 删频道会回报连坐数量 ✓

`ok` 回执里多了 `removedChildren` ✓
客户端在**弹窗里就得写出会连坐几个** ✗ 不能默默连坐 ✓
那是最容易让人丢数据的方式 ✓

新增 `test-subchannel.mjs`（9 项）—— 见客户端 CHANGELOG 的说明 ✓
## 1.8.0

### 消息置顶（服务端部分）

`messages` 表加两列：`pinned_at`（NULL = 没置顶）+ `pinned_by` ✓

**⚠️ 为什么放在 messages 上、不单开一张 pins 表** ✗
单开表的话消息被删就得靠级联去清 ✓（`reactions` 那张表就是这么办的 ✓）
而"置顶"本质是消息的一个**属性** ✓ 一条消息在一个频道里只有一个状态 ✓
放同一行天然跟着消息走 ✓ 不用级联、不用 join、也不会有孤儿 ✓

**⚠️ 但列表接口必须单独做** ✗
置顶的往往正是很久以前那条重要消息 ✓
而客户端只加载了最近 50 条 ✓ 在本地筛会显示成空的 ✓

```
客户端 → { type:'pin', messageId }            （toggle ✓）
服务端 → { type:'pinned', channelId, messageId, pinnedAt }
新增   → GET /api/channels/:id/pinned
```

**三个刻意的决定** ✓

① 广播里**只带 id 和时间**，不带整条消息 ✗
   那条消息可能根本没被加载过 ✓ 带过来客户端也不好往哪儿塞 ✓
   客户端拿它修补已加载的那条 ✓ 需要完整内容时自己去拉列表接口 ✓

② 列表顺序按 **`pinned_at` 倒序，不是消息 id** ✗
   按 id 排的话，新置顶一条三个月前的消息会掉到列表最底下 ✓ 用户根本找不到 ✓
   ⚠️ 测试里必须**倒着置顶两条**才验得出来 ✓
      顺着置顶的话，按 id 排和按时间排的结果**一模一样** ✓ 测了等于没测 ✗

③ 每频道上限 **50 条** ✓ 到上限时回 `pin_limit` ✗
   **必须明确报错** ✓ 不然用户只看到"点了没反应" ✓ 会以为坏了 ✓
   上限只挡"加" ✗ 不挡"减" ✓ —— 满了之后仍然要能取消置顶 ✓

**⚠️ 第三条信息泄露路径** ✗（前两条是 `reply_to` 和 `react`）

置顶列表是**单独一个 HTTP 接口** ✓ 鉴权必须和历史接口**完全一样** ✗
不挡的话，任何人拿到一条私聊 id 就能读到它的置顶 ✓
**而置顶的往往正是"最重要、最不想外传"的那几条** ✗ 后果比读历史还严重 ✓

新增 `test-pin.mjs`（8 项）：

- 置顶一条 → 广播带时间戳；置顶列表里能读到它
- 同一条再置顶一次 → 取消（pinnedAt 为 null，列表清空）
- ★ 后置顶的排前面（**哪怕它的消息 id 更小** ✗）
- 置顶列表里的消息和聊天里一样：带引用摘要和表态
- 置顶的消息被删之后自动从列表里消失
- ★ 到 50 条上限时明确报错（不能"点了没反应" ✗）
- ★ 私聊的置顶列表：非会话成员读到 403
- ★ 非会话成员不能置顶私聊消息（而且不能真的改掉状态 ✗）
## 1.7.0

### 消息 emoji 表态（服务端部分）

新表 `reactions` ✓ 主键是「消息 + 人 + 表情」三件套 ✓
- 同一个人对同一条消息点同一个 emoji 天然**幂等** ✓ 再点一次就是取消 ✓
- 而一个人可以对同一条消息点**好几个不同**的 emoji ✓（Discord 就是这样 ✓）

```
客户端 → { type:'react', messageId, emoji }
服务端 → { type:'reactions', channelId, messageId, reactions }
消息上的 reactions 形状：[{ emoji, users:[{id,name}] }]
```

**三个刻意的决定** ✓

① **没有 `count`、也没有 `mine`** ✗
   `count` 就是 `users.length` ✓ 多存一份迟早不一致 ✓
   而 `mine`（我点过没有）**对每个人都不一样** ✗
   服务端下发的是同一条广播 ✓ 它算不出一个对所有人都对的 `mine` ✓
   所以只给 `users` ✓ 客户端自己判断 ✓

② **名字实时 join `members`** ✗
   表里存了一份 `user_name` 只作兜底 ✓
   直接用它会出问题：人改了昵称之后**旧表态里还挂着老名字** ✓

③ **广播前重读一遍** ✗ 不要手工"上一个状态 ±1" ✓
   两个人同时点的时候手工算很容易和库里对不上 ✓
   界面上的数字一旦错一次，就得等下次重新拉历史才修得回来 ✓

**⚠️⚠️ 第二条信息泄露路径** ✗（第一条是 `reply_to`）

```
不校验频道可见性的话：
  任何人拿一条【私聊】消息的 id 发一条 react
  服务端照常广播 → 广播里带着【参与者昵称】
  → 公开频道里每个人都能看到"某条你不认识的消息上有谁谁谁"
```

比 `reply_to` 那条泄露得少 ✓ 但**是同一种疏忽** ✓
所以判法和发消息**完全一致**：私聊必须是会话成员 ✓
而且连库都不该写进去 ✓（测试里直接开库数了行来证明这一点 ✓）

新增 `test-reactions.mjs`（8 项）：

- 表一条 👍 → 广播里带上是谁点的（id + 名字）
- 同一个人再点同一个 → **取消**（不是又加一条）
- 一个人可以点多个不同的 emoji
- 两个人点同一个 → 合并成一项、users 有两个
- 排序：人数多的排前面（一眼能点到常用的那个）
- ★ 私聊消息的表态**不能广播给非会话成员**（且根本没写进库）
- 表态一条不存在的消息 → 静默忽略、不报错
- 消息被删之后表态**级联删掉**（直接开库数行验的 ✓ 界面看不出来 ✗）

⚠️ 第 3 条第一次跑是**红的** ✗ 但那是**测试的期望写错了**：
`sort()` 按 UTF-16 码位排 ✓ `🎉`(U+1F389) < `👍`(U+1F44D) ✓
而期望值写死成 `['👍','🎉']` ✓ 改成两边都排就没有这个假设了 ✓
## 1.6.0

### 消息引用回复（服务端部分）

`messages` 表加 `reply_to INTEGER` 列 ✓ 走 `migrate()` 给老库补上 ✓
（老消息一律是 NULL —— 它们本来就不是回复 ✓ 语义正确 ✓）

协议：`{ type:'message', channelId, body, attachment, replyTo }` ✓
下发的消息多两个字段：`reply_to`（id ✓）和 `reply_preview`（摘要 ✓）

**⚠️⚠️ 同频道校验是必须的 —— 这是一条真实的信息泄露路径** ✗

```
不校验的话：
  任何人在【公开频道】里发一条 replyTo = 某条【私聊】消息的 id
  服务端把摘要一填 → 私聊内容就出现在公开频道里了
```

所以 `listMessages` 和插入时都**只回填"确实属于该频道"的摘要** ✓
其余一律留空 ✓ 界面上显示"原消息不存在" ✓ 不区分"被删了"和"不属于这里" ✗
区分了就等于告诉别人"那个 id 上曾经有条消息" ✓ 那正是要避免的 ✓

校验不过时**不报错、只忽略 replyTo** ✓
报错的话客户端还得处理一种新错误码 ✓ 而用户也没法自愈 ✓ 直接当普通消息发更简单 ✓

**摘要由服务端解析** ✓ 不能让客户端自己找 ✗ ——
被引用的消息很可能**不在已加载的那一页里** ✓（往前翻很久才引用得到的老消息 ✓）
客户端自己找会找不到 ✓ 只能错误地显示"原消息不存在" ✓

新增 `test-reply.mjs`（5 项 ✓ 其中两项专测泄露路径 ✗）：
- 正常回复：reply_to 存住、预览带上原作者的昵称和正文
- ★ 私聊消息不能被引用到公开频道
- ★ 另一个频道里的普通消息也不能跨频道引用
- 引用一条不存在的消息 → 忽略、不报错
- 原消息被删之后：reply_to 还在，reply_preview 变 null
## 1.5.0

### 新增 P2P 连通性诊断页

投屏现在全走 SFU，而服务器出口只有 6 Mbps —— 4 Mbps 一档**只够一个人看**。
改成 P2P 直连可以完全绕开服务器带宽，但"能不能直连"取决于双方的 NAT 类型、
有没有 IPv6、同不同运营商。这些**只有在真实网络里量过**才知道，所以先做诊断。

新增两个**纯增量**的路由（现有 `/ws` 一个字节没改）：

| 路由 | 作用 |
|---|---|
| `GET /p2p-check` | 自包含的诊断页，无外部依赖 |
| `GET /p2p-signal` | 房间式信令中继，需带对邀请码 |

页面在真实网络里回答四个问题：

1. **本机**：公网 v4/v6 地址、UDP 出站通不通、**NAT 映射行为**（锥型还是对称型）
2. **STUN**：国内到底哪些服务器可达 —— 逐个实测，不照抄网上的列表
3. **直连**：两人之间能不能打通、用了几秒、走的是哪一类候选对
4. **吞吐**：打通之后**实际**能跑多少 Mbps

第 4 项是决定性判据 —— **能连不等于能扛 4 Mbps 投屏**。

NAT 映射行为的判法：用**两个不同 IP** 的 STUN 各抓一次候选，比较映射出去的端口。
端口一致 → 端点无关映射（锥型，打洞成功率高）；端口不同 → 对称型（打洞很难）。
这样不用实现 STUN 协议，靠浏览器原生的 ICE 就能测出来。

### 写这个页面的过程中，测试抓出来五个 bug

| bug | 现象 | 原因 |
|---|---|---|
| **被叫收不到 offer** | 只看到"15 秒没建立连接" | 握手处理写在 `startP2P()` 里 → 只有点过按钮的那边装着 handler。改成挂在**连接信令之后** |
| **候选被丢掉** | 本机明明有 host 候选，却报 `host=0` | `Promise.race` 的超时分支返回**空数组**，把已收到的候选全扔了。改成超时也返回已收集的 |
| **成功路径不出结论** | 连上之后永远停在"已直连" | 只写了失败分支的 `finish()`，成功分支漏了 |
| **吞吐测歪 52 倍** | 报 5.37 Mbps（实际 279.59） | 读的是灌数据**停止之后**那一秒 = 缓冲区排空。改成 START/STOP 标出的明确计时窗口 |
| **本机两个实例连不上** | 测试环境专属 | Chromium 默认把本地 IP 藏成 mDNS 名字，而它的 responder 要占 UDP 5353，两个实例抢不到。测试里加 `--disable-features=WebRtcHideLocalIpsWithMdns` |

最后一条**只影响测试环境** ✓ 真实场景是两台电脑，不冲突。

### ★ 部署到真实网络之后，又抓到一个：NAT 判法错了两次

页面部署上去之后，某台机器被判成「**地址/端口相关（对称型）**，打洞很难」，
可**同一台机器实测 108ms 直连成功、102 Mbps** ✗ 明显矛盾。
对称型 NAT 不可能这么快打通 ✓ 所以是**推断错了**，不是实测错了 ✓

| 次数 | 错法 | 为什么错 |
|---|---|---|
| **第一次** | 建**两个** RTCPeerConnection、各配一台 STUN，比较映射端口 | 每个连接用的是**不同的本地端口** ✓ 而 NAT 映射跟着本地端口走 ✓ 所以连最标准的锥型 NAT 也一定比出"不一样" ✗ → 一律误判成对称型 |
| **第二次** | 改成**一个**连接配多台 STUN，然后**数候选的个数** | Chrome 会把**映射地址相同**的候选**去重** ✓ 锥型下 5 台 STUN 看到的是同一个映射 ✓ → 只留**一个**候选 ✓ 于是"只有 1 个"被读成"只有 1 台回了" ✗ 又判反了 |

**正确判法**：一个连接配多台 STUN，拿「实际响了几个**不同**映射」
和「**应该**有几台会回（已知可达的那几台）」对比：

```
问了 N 台，拿到 1 个不同映射  →  端点无关（锥型）✓ 打洞最容易成功
问了 N 台，拿到 N 个不同映射  →  地址相关（偏对称型）⚠️ 可能困难，但不等于打不通
问了 N 台，拿到中间值         →  介于两者之间
```

修完实测（`39.187.69.143`）：**锥型** ✓ 访问 5 台 STUN 映射地址完全一致 ✓

**这段逻辑的教训**：**推断出来的结论必须和实测结果对账** ✗
对不上就是推断错了 ✓ 不是实测错了 ✓

配套：

- 新增 `voice-client/scripts/verify-nat-detect.mjs` 专门守这段逻辑 ✗
  —— 常驻测试为了让连接快一点会**清空 STUN 列表** ✓
  于是这段比较逻辑在它里面**根本执行不到** ✓ 必须单独探 ✓
- 页面初始化改成**先测 STUN、再探本机** ✗
  —— 反过来的话判法只能退回用户填的列表 ✓ 里面混着不可达的 ✓ 结论不准 ✓
- 第 2 节加了一句提示：**NAT 分类只是参考，以第 4 节的实测结果为准** ✓

### 🔒 安全修复：改个昵称就能抢走频道主

**这是个真实的提权漏洞，而且已经造成过实际后果**
（服务器上曾经一次出现 3 个都叫频道主名字的成员）。

#### 漏洞是怎么成立的

两个问题凑在一起：

**① 昵称等于 `OWNER_NAME` 就自动提拔成频道主**

```js
// 改之前
if (isWantedOwner) role = 'owner';
// 而且 makeOwner 会把原来的频道主降级成 admin
```

`OWNER_NAME` 是配置在 `.env` 里的（例如 `Owner`），
而**任何成员都能在设置里把昵称改成它** —— 于是谁都能把自己提成频道主，
还会把真正的频道主踢下去。

**② `userId` 对但 `userKey` 不对时，服务端静默新建一个成员**

```js
// 改之前
if (existing && existing.user_key !== userKey) {
  userId = randomUUID();   // ← 直接建一个新的
  existing = null;         // ← 而且名字采信客户端传的
}
```

两条加在一起：随便编个 userId + 随便编个 key + 名字填 `OWNER_NAME`，
就能凭空造出一个**频道主**。

#### 改成了什么

| 位置 | 现在的行为 |
|---|---|
| `db.js` `registerMember` | 只有**还没有频道主**时才按昵称认领（首次搭建）。已经有频道主之后，昵称再也换不来角色 |
| `index.js` hello 处理 | key 不对 → **名字不采信**，换成中性的「用户XXXX」，角色一定是 `member` |
| `index.js` hello 处理 | 别人报频道主的名字 → 同样换成「用户XXXX」（**名字由频道主独占**） |

#### ⚠️ 代价：换电脑拿回频道主不再是自动的

以前"名字对上就能拿回频道主"。现在这条路堵死了（它本身就是漏洞），
改成在服务器上跑一条命令：

```bash
# 1. 在新电脑上装好、连上去（会得到一个全新身份）
# 2. 在名单里找到那个新身份的 userId
./member.cmd list
# 3. 提成频道主
./member.cmd promote <新身份的 userId>
```

> `member.cmd` 会 ssh 到服务器执行 `src/fix-member.mjs`（会问一次密码）。

#### 验证

新增 `test-identity.mjs` —— **端到端**，起真服务端 + 真 WebSocket：

```
✅ ① 还没有频道主时，昵称对得上 → 拿到 owner（首次搭建）
✅ ② ★ 已经有频道主了，另一个人也叫 Owner → 只能是 member
✅ ③ 原来的频道主没被顶掉
✅ ④ ★ 已有成员把昵称改成 Owner → 角色不变（这才是提权口子）
✅ ⑤ ★ userId 对、key 错 → 不能顶掉频道主
✅ ⑥ ★ 冒充时名字不被采信
✅ ⑦ 冒充进去的人角色是 member
✅ ⑧ ★ 不管怎么折腾，全服只有一个 owner
✅ ⑨ 全服名册里没有重复的 OWNER_NAME
```

9/9 通过。

> 写第一版补丁时漏了「还没有频道主」这个条件，结果**谁也拿不到频道主** ✗ ——
> 测试 ① 当场抓到，已修。
