**关掉之后到底发生了什么**（这是设计上最要紧的一点 ✗）：

| | 开（默认） | 关 |
|---|---|---|
| 建 RTCPeerConnection | 建 | **不建** |
| 发 want / offer 协商信令 | 发 | **不发** |
| 收到对方的 P2P 信令 | 处理 | **整条忽略** |
| 画面走哪 | 直连成功就直连 ✓ 失败才回退服务器 | **一律服务器中转** ✓ |

⚠️ 「关」的含义是**完全不走直连** ✗ —— 不是"建了连接但不用" ✓
两者对用户是一样的（画面都走服务器 ✓）但前者会白发协商信令、白开端口 ✓

**徽章**：新增 `p2p.off`「经服务器（直连已关）」✓
- ⚠️ **不能**借用 `relay` 的「经服务器」✗ —— relay 配的提示语是"打不通"✓
  自己关掉的人看到那句会跑去排查一个**不存在**的网络问题 ✗
- ⚠️ **也不能**借用 `idle` 的「未建立直连」✗ —— 那句听起来像"还没连上、在等"✓
  而实际上**永远不会连** ✓ 会让人白等 ✓
- 颜色用**无色** ✗ 不是 warn ✓ —— warn 是"有事要你注意"，而这是他自己的选择 ✓

**★ 而真正指向问题的，是用户那句括号** ✗
> 先显示直连然后**迅速**显示经服务器

**"连上了又掉"** 和 **"根本连不上"** 是**完全不同**的两个问题 ✓
而"迅速"这个词把它从网络问题指成了**代码问题** ✓✓

---

### 根因：两个 bug 叠在一起 ✗

**Bug A ✗ —— 主动拆连接被误判成"直连失败"**

```ts
} else if (st === 'failed' || st === 'closed') {
//                          ^^^^^^^^^^ 这个不该在这里 ✗
  this.setState(peerId, 'failed')
```
`connectionState === 'closed'` **只可能**来自**我们自己**调了 `pc.close()` ✓
（对端断开是 `failed` 或 `disconnected` ✓ 不会是 `closed` ✓）
而 `pc.close()` 恰恰是 `unwatch()` / `stop()` 里拆连接时做的事 ✓
→ **每次正常拆除都在界面上留下一条"直连失败"** ✗ → 徽章变「经服务器」✓

**Bug B ✗ —— 每几秒把刚建好的直连拆掉重建**

```tsx
// App.tsx（修改前）
const myShareStream = useMemo(() => {
  const mine = screenShares.find((s) => s.isLocal)
  const t = mine?.track.mediaStreamTrack
  return t ? new MediaStream([t]) : null   // ← 每次都造一个**新对象**
}, [screenShares])                          // ← 而它**每次 LiveKit 推送都变**
```
`screenShares` 是每次推送都变的新数组 ✓ → 每几秒产生一个**新的 `MediaStream`** ✓
而里面装的**轨道是同一条** ✓ → `useScreenShareP2P` 的 effect 依赖整个 `myStream` ✓
→ **每几秒重跑一次：先 `bc.stop()`（内部 `pc.close()`）再新建** ✗✗

**两个 bug 合起来就是你看到的现象** ✓
```
连上 → 徽章「直连」✓
几秒后 LiveKit 推一次 → 流对象换新 → effect 重跑 → 把连接拆了 ✗
拆的时候 pc.close() → 被 Bug A 判成 failed → 徽章「经服务器」✗
而且重建还没来得及连上就又被拆 ✓ → 观看端一直回退到 LiveKit ✓
→ **服务器上多出整整一个码率** ✓（2.6 Mbps ✓ 和实测吻合 ✓）
```

---

### 修法 ✓（三处，缺一不可 ✗）

| # | 改哪 | 怎么改 |
|---|---|---|
| **A** | `p2pTransport.ts` ×2 处 | `'closed'` 不算失败 ✓ 只认 `'failed'` ✓ |
| **B1** | `App.tsx` | 依赖**轨道**而不是"盛放它的数组" ✓ `useMemo(..., [myShareTrack])` ✓ |
| **B2** | `screenShareP2P.ts` | effect 也只看**轨道** ✓ 流对象走 ref ✓（双保险：这个 hook 是通用的 ✓ 以后谁传个不稳定的流进来都会踩同一个坑 ✓） |

### 几个实现决定 ✓

| 决定 | 为什么 |
|---|---|
| 语言状态包在 **main.tsx** 里，不是 App 里 ✗ | App 的 return 是两千多行的一棵 JSX ✓ 在外面包 Provider 就得动它的头尾 ✓ 纯属不必要的风险 ✓ 包在入口的话 App **一行都不用改** ✓ |

对朋友来说"他在打排位"比"他在听某个 BGM"有用得多。

#### ⚠️ 只做一件事：查进程在不在

```
detect-game.ps1  ←  比对一张内置白名单（约 35 个常见游戏）
```

**不读游戏内存、不注入、不 hook、不装键盘钩子、不做 overlay。**
这是任务管理器在做的事，Discord / Steam / OBS / 微星小飞机全都在做。

> 之前查 LoL 快捷键问题时我考虑过**低级键盘钩子**（`WH_KEYBOARD_LL`）——
> 幸好没走那条：全局键盘钩子恰恰是反外挂会盯的东西。
> 最后用的是计划任务提权（`RegisterHotKey`），温和得多。

**只比对白名单**，不分析全部进程 —— 有些恶意软件也用同样的 API 枚举进程，
扫全表更容易被安全软件盯上。

#### 隐私：关掉就**真的停掉**

关掉开关时主进程**把那个 PowerShell 子进程杀掉** —— 不是"读了不上报"。
实测过：起应用后能看到**两个** powershell 子进程、父进程都是 electron：

```
PID 21468  -File ...\detect-game.ps1 "league of legends,cs2,…"  ← 游戏
```

原来「解析失败」和「明确表示没有」都返回 `null` ✗ —— 于是 PowerShell 混进来
**任何一行警告**，界面上就会闪一下"没在听" ✗

现在分三种：有内容 / `null`（明确没有）/ `undefined`（没看懂，**保持原状**）。

#### 数据从哪来：Windows SMTC

不碰任何播放器的私有接口，走的是 **SMTC（系统媒体控制）** ——
就是按音量键弹出来那个"正在播放"面板的数据源。
歌名、歌手、播放状态都是它给的，网易云、Spotify、浏览器里的视频通用。

**没有写原生模块**。SMTC 是 WinRT API，Node 碰不到，但 PowerShell 5.1
能直接投影 WinRT 类型 —— 所以只要常驻一个 PowerShell 子进程读就行。

> 常驻是必须的：PowerShell 启动要 200~500ms 且吃 CPU，
> 每 3 秒起一个太浪费。常驻只付一次启动成本。

#### 三个踩过的坑（都写进脚本注释了）

1. `[System.WindowsRuntimeSystemExtensions]` 要先
   `Add-Type -AssemblyName System.Runtime.WindowsRuntime` 才有
2. `[Console]::OutputEncoding = UTF8` —— 不设的话**中文歌名经管道出去全是乱码**
3. `.ps1` 必须 **UTF-8 带 BOM** —— 无 BOM 时 PS 5.1 按 ANSI 解析脚本本身

#### ★ 隐私：关掉就**真的停掉**

关掉开关时，主进程**把检测子进程整个停掉** ——
不是"继续读但不上报"。后者隐私是假的：进程还在跑、数据还在拿。

`activity` 的全部内容也当作**不可信输入**处理（它是客户端提供、
然后广播给所有人的）：只认 `music`、title 截 120 字、artist 截 80 字。
不然别人可以塞几十万字把所有人的界面撑爆。

## 0.29.0

### 「以后都自动以管理员启动」—— 靠计划任务，只授权一次

0.25.0 加了「以管理员重启」，但那是**一次性的** ——
开机自启拉起来的那一份还是普通权限，游戏里快捷键照样不灵，
每次都得手动去设置里点一下。太蠢了。

现在多一档 **「设为默认」**：

```
设置 → 通用 → 游戏兼容
  普通权限运行                                    [以管理员重启]
  默认以普通权限启动 / 已设为默认以管理员启动        [设为默认]
```

点「设为默认」会弹**唯一一次** UAC，建一个"以最高权限运行"的计划任务。
之后每次启动都靠它静默提权，**不再弹任何东西**。

#### 原理

Windows 允许**中等权限的进程触发一个已注册的高权限任务** ——
任务自己以高权限启动，全程不弹 UAC。代价只是建任务那一次要授权。

> 计划任务用 `/SD 01/01/2000`（一个早就过去的日期）——
> 它**永远不会自己触发**，只在我们显式 `/Run` 时才跑。

#### ⚠️ 三道防无限重启的保险

自动提权最怕"检测到没提权 → 重启 → 还是没提权 → 再重启"。所以：

1. **命令行带 `--from-task`** → 这次就是从任务里起来的，不再重启
2. 已经在管理员权限下 → 不需要重启
3. 任务没注册 → 没什么可触发的

第 1 条是关键：任务的目标写的是 `"...\Voice.exe" --from-task`。

#### 一个绕开的坑

## 0.27.0

### 输入框变大，按钮收进框里

```
以前：  [ 输入框… ]  [😊] [📷] [📎] [发送]        ← 一行横排
现在：  ┌──────────────────────────────┐
        │ 输入文字…                     │
        │               [😊][📷][📎][发送] │
        └──────────────────────────────┘
```

两个毛病一次解决：

- **输入框被挤得又矮又窄** —— 写两句就得在里面左右滚。
  换成 `textarea` 并随内容长高（最多 8 行左右，再高就把聊天记录挤没了）。
- **按钮在外面像另一排控件** —— 视线得在"打字"和"按钮"之间来回跳。
  收进盒子里之后，整块是一个东西。

#### 两个细节

**① 自动长高的关键是"先把 height 设成 auto"**

```js
el.style.height = 'auto'          // ← 不重置的话 scrollHeight 只增不减，删字后高度回不去
el.style.height = el.scrollHeight + 'px'
```

发出去之后要收回来 —— 这件事交给 `useEffect` 看 `draft` 变空来做，
因为 `onChange` 里拿不到"发送后"那一刻（那时 value 还是旧的）。

**② 换成 textarea 之后，回车必须显式处理**

`<input>` 里回车本来就不会换行，所以以前的 `onKeyDown` 只是"顺手"。
`<textarea>` 里**回车默认就是换行** —— 不显式拦，按回车就变成加一行而不是发出去。
（`Shift+Enter` 换行保持不变。）

### 语音频道

**⑤ 成员顺序乱跳**
根因：**LiveKit 返回参与者列表的顺序不保证稳定**，
而服务端每 3 秒推一次快照 —— 于是同一个房间的人前后跳。
现在服务端按 `joinedAt` 排序，客户端再用 `byJoinOrder` 兜一层
（`joinedAt` 缺失时按 identity 定序，**至少"不再变"**）。

**⑥ 麦克风 / 喇叭状态改成状态灯**

原来是 🎤 / 🔇 两个 emoji，问题有两个：emoji 的字形宽度和基线**由字体决定**，
不同人之间对不齐；而且只有"开/关"两种状态。

| 灯 | 含义 |
|---|---|
| 🟡 黄 | 闭麦 |
| 🔴 红 | 闭麦 + 关了喇叭 |
| ⚪ 灰 | 开麦但没说话 |
| 🟢 绿 | **正在说话**（带光晕） |
| 🔵 蓝 | 在投屏（在麦克风灯的**左边**） |

- 投屏灯的位置**恒定占位**（不投屏时留空）—— 否则右边那个麦克风灯会被推来推去，
  而要求是**所有人的麦克风灯竖向对齐**。
- "正在说话"走 LiveKit 的 `ActiveSpeakersChanged`（几百毫秒级），
  **不是**服务端那 3 秒的快照 —— 用后者会把状态拖成幻灯片。
- "关了喇叭"通过 participant attribute 广播（服务端快照本来就会带回 attributes）。

**⑦ 对自己右键不再弹菜单**
那个菜单只有"调音量"一项，而调自己的音量没有意义。

**⑪ 英雄联盟里快捷键失效**

根因**不是我们的 bug**：LoL 通常以**管理员权限**运行，而 Windows 的 UIPI
会挡住普通权限程序的全局热键（`RegisterHotKey` 在高权限窗口前台时根本不触发）。
Discord、AutoHotkey 都有同样的坑。

所以：设置 → 通用 → **游戏兼容**里显示当前权限，并提供**「以管理员重启」**

## 0.23.0

### ① 修复：打开投屏后聊天框自己跳到中间

**现象**：开始看投屏，聊天框被画面的出现挤了下去 —— 但滚动位置**没有跟着走**，
停在了历史的中间，得手动拉到最底下。

#### 根因：`ResizeObserver` 只观察了一半

0.22.1 修"打开软件停在最上面"时，我加了一个 `ResizeObserver` ——
但它**只观察了内容**（`inner`）：

```
inner 变高  →  图片加载出来、文字换行变多   ✅ 会触发
el    变矮  →  投屏占掉上半屏，聊天区被压小  ❌ 不触发
```

而 `scrollTop` 是一个**像素值**。容器一变矮，同样的 `scrollTop`
对应的位置就跑到中间去了 —— 看起来就是"聊天框自己跳到了中间"。

**修法：两个都观察。**

```tsx
const ro = new ResizeObserver(pin)
ro.observe(inner)   // 内容变高
ro.observe(el)      // 容器变矮 ← 补上这个
```

> 值得记一笔：同一个 `ResizeObserver`，少观察一个元素，
> 就漏掉了一整类情况。**"内容变了"和"容器变了"是两件事**，
> 而对滚动位置来说它们的影响是一样的。

## 0.22.1

### 修复：每次打开软件都停在聊天框**最上面**

---

#### 根因不是"没滚"，而是"**滚的时机不对**"

原来的代码是这样：

```tsx
// 消息条数变化时滚到底
useEffect(() => {
  if (el) el.scrollTop = el.scrollHeight
}, [messages.length])
```

看着没问题 —— 消息从 0 条变成 N 条，确实滚了一次。

**但图片是一张一张加载的。**

```
设置 scrollTop 的那一刻    下面几张图还没加载出来，高度算 0
        ↓
滚动位置 = 当时的"底部"
        ↓
图片陆续加载完              内容被顶高几百上千像素
        ↓
而滚动位置**不会跟着走**  →  人停在半路
```

图多的时候，被顶下去的距离接近整屏 —— 看起来就是"停在了最上面"。

**所以只在消息条数变化时滚一次是不够的**，图片加载、字体切换、
窗口变窄导致换行，都会改变内容高度。

#### 修法：盯着**内容高度**，而不是消息条数

```tsx
const ro = new ResizeObserver(() => {
  if (stickRef.current) el.scrollTop = el.scrollHeight
})
ro.observe(inner)   // ← 观察**内容**容器
```

⚠️ 这里必须多套一层 `div`：`ResizeObserver` 观察的是元素的**边框盒**，
而滚动容器本身是 `flex: 1`（高度固定），**观察它什么也看不到**。
真正会长高的是里面的内容。

（顺带确认过：没有任何 CSS 依赖"消息是滚动容器的直接子元素"，多这层是安全的。）

---

#### 顺带修掉一个更早就存在的问题

原来的效果是「**总是滚**」—— 命令注释里也写着"这里简化成总是滚"。

后果是：**你往上翻着看历史记录，只要有人发一条新消息，就被拽回底部**，
得重新往下翻。图片加载的时候也一样。

现在加了"贴着底部"的判断：

| 状态 | 来新消息时 |
|---|---|
| 贴在底部 | 跟着滚下去 ✅ |
| 翻着历史 | **不打扰**，自己翻回去看 |

容差给了 40px —— 完全贴底才算的话，一点点抖动就解除跟随了。

换会话（切频道、开关私聊）时仍然**无条件回到底部** ——
那是另一回事，不该保留上一个会话的滚动位置。

## 0.22.0

### 新增：图片在**应用内**看，带缩放和下载

**之前**：点聊天里的图片 → `shell.openExternal` → **图片跑到系统浏览器里去了**。
看个截图还要切窗口、关标签页，想存下来还得在浏览器里再操作一次。

**现在**：点图片 → 应用内全屏看图器。

---

#### 交互

| 操作 | 效果 |
|---|---|
| **滚轮** | 缩放，**以光标为中心** |
| **按住拖动** | 平移 |
| **双击** | 在「适应窗口」和「原始大小」之间切换 |
| `−` / `＋` 按钮 | 以画面中心缩放 |
| 适应窗口 / 原始大小 | 一键定位 |
| ⬇ 下载 | 弹系统原生「另存为」 |
| Esc / 点背景 / ✕ | 关闭 |

#### 为什么滚轮要**以光标为中心**

这是个很容易做错、但错了就特别难受的细节。

如果以**画面中心**缩放，你想看右下角的小字、把鼠标移过去滚滚轮 ——
内容会朝中心跑，**想看的地方越放越偏**，得一边缩放一边拖回来。

以光标为中心的话，鼠标指着哪就放大哪，这才是「放大镜」该有的手感。

实现上就是让光标底下那个像素**待在原地**：

```
屏幕上某点的位置 = offset + scale × 图上坐标
反解出光标下的图上坐标，再让它在新的 scale 下映射回同一个屏幕位置
```

#### 为什么百分比显示的是**真实像素比例**

一张 3840 宽的截图缩到窗口里大概是 **25%**；放到 **100%** 才是
**一个图像像素对一个屏幕像素**。

如果按「相对适应窗口的倍数」显示，用户没法知道什么时候该停 ——
**而看截图的小字，要的正是「到 100% 了」这个明确的点**。

到了 100% 以上还会把 `image-rendering` 切成 `pixelated` ——
看文字截图时，模糊的平滑插值还不如硬边清楚。

#### 下载走的是应用自己的流程

新增了 `app:download`（主进程 `webContents.downloadURL`），
**不是** `openExternal`：

| | 行为 |
|---|---|
| `openExternal` | 把 URL 丢给浏览器，下载也在浏览器里 |
| `downloadURL` | 弹 Electron 的原生「另存为」，存完还在应用里 |

默认文件名来自服务端的 `Content-Disposition`（那边设了 `filename*=UTF-8''…`，
中文名也能正确带上），所以不用自己猜。**不设 `savePath` 时 Electron 才会弹对话框** ——
设了就直接静默写盘了，这一点很关键。

#### 只改了图片

**非图片附件**还是走原来的 `onOpenFile`（用系统程序打开 / 浏览器下载）——
对 zip、pdf 这类东西，交给系统处理比自己实现一个预览器合理。

## 0.21.2

### 修复：发出去的图片显示「🖼 xxx.png（已被删除）」

**现象**：截图或传图明明成功了（消息发得出去），但聊天里显示成
`🖼 截图-xxx.png（已被删除）`，**看起来像文件真的被删了**。

---

#### 根因：CSP 的 `img-src` 没有放开 http:

```html
<!-- index.html -->
img-src 'self' data: blob:          ← 没有 http: / https:
```

而图片地址是 `<img src="http://<服务端>/api/files/xxx">` —— 和页面**不同源**，
所以被 `img-src` 挡掉，`<img>` 触发 `onError`，
组件就把它当成"文件被删了"，显示成那个样子。

**上传链路本身完全正常**（服务端的 `GET /api/files/:id` 也确实没有鉴权、
`<img>` 能直接取）。坏的只有"显示"这一步。

#### 这个 bug 的迷惑之处

**它伪装成"文件被删了"。** 而实际情况是文件好好的，
只是**浏览器不让我们把它显示出来** —— 组件里那句"已被删除"是我写的兜底文案，
把 CSP 拦截误判成了删除。以后要是再看到这个提示，先怀疑 CSP。

（讽刺的是 `index.html` 里那段注释**专门解释了为什么 `connect-src` 必须放开**，
但 `img-src` 被漏了 —— 因为当时只想到 fetch 和 WebSocket，没想到图片。）

---

#### ⚠️ 这已经是**第二个 CSP 引发的 bug** 了

上一个（0.21.1 的截图失败）是 `connect-src` 拦了 `fetch(dataUrl)`，
这个是 `img-src` 拦了跨源图片。

**两个指令各管各的，而且名字很像，特别容易搞混：**

| 指令 | 管什么 | 我们栽过的坑 |
|---|---|---|
| `connect-src` | `fetch` / `XMLHttpRequest` / WebSocket | 对 `data:` URL 调 fetch → 被拦，报 `Failed to fetch` |
| `img-src` | `<img>` 标签的 `src` | 加载服务端图片 → 被拦，界面显示"已被删除" |

**`img-src` 里的 `data:` 管不到 `fetch`；`connect-src` 里的 `http:` 也管不到 `<img>`。**

**两个 bug 的共同点：报错信息都完全指不到 CSP。**
一个说"网络失败"，一个说"文件已删除"。所以 `index.html` 的 CSP 注释这次写全了，
把两个坑都记在里面。

---

#### 验证方式

`img-src` 到底管不管跨源图片，不能靠猜 —— **实测**：

1. 从**构建产物**里抠出真实的 CSP（不抄一份，免得测的不是线上那个）
2. 用旧 CSP（没有 `http:`）跑一次 → Chromium 明确报
   `Refused to load the image ...` ✅ **根因确认**
3. 用构建产物里的新 CSP 直接加载**真实的应用页面** → 同一个图片请求
   **发出去了**（拿到 404，因为我故意用了不存在的 id），
   **没有任何 CSP 拦截记录** ✅ **修复确认**

> 中间还踩了个测试自己的坑：第一版判定逻辑把"页面压根没加载起来"
> 也当成了"没被拦 = 通过"，是个**假阳性**。改成"加载失败 = 无结论"才对。
> 测试写错了比不写更糟 —— 它会给你一个绿灯。

## 0.21.1

### 修复：截图报 `Failed to fetch`

**现象**：点截图按钮、框选完区域，提示 **`Failed to fetch`**。

---

#### 根因：对一个 `data:` URL 调了 `fetch`，被 CSP 挡掉

`ChatPanel.tsx` 里原来是这么写的：

```ts
// 把 dataURL 变成 Blob
const blob = await (await fetch(shot.dataUrl)).blob()
```

看起来最顺手，但 **`fetch` 一个 `data:` URL 走的是 CSP 的 `connect-src`**，
而 `index.html` 的 CSP 里：

```
connect-src 'self' http: https: ws: wss:      ← 没有 data:
```

**所以它被 CSP 直接挡掉**，抛出来的错误就是 `TypeError: Failed to fetch`。

#### 为什么这个 bug 特别难查

**错误信息完全看不出跟 CSP 有关系。** 「Failed to fetch」的教科书含义是
"网络连不上 / 服务器没起来 / CORS 被拒"，所以第一反应一定是往那个方向查 ——
而实际上网络、服务器、CORS 全都是好的。

还有一个很像的陷阱：

```
img-src 'self' data: blob:      ← 这个只管 <img> 标签
connect-src 'self' http: ...    ← fetch 归它管
```

**两个指令长得像，很容易以为"data: 我已经放开了"。**

#### 修法：自己解 base64，不碰网络栈

```ts
const binary = atob(body)
const bytes = new Uint8Array(binary.length)
for (let i = 0; i < binary.length; i++) bytes[i] = binary.charCodeAt(i)
return new Blob([bytes], { type: mime })
```

纯计算，没有 CSP 什么事 ✓

> `atob` 那一步**必须逐字节搬到 `Uint8Array`** ——
> 直接 `new Blob([binary])` 会把每个字符当成一个 UTF-16 码元，
> 0x80 以上的字节全部损坏（图能生成，但打不开）。

#### 顺带加了单测

`npm test` → `scripts/test-dataurl.mjs`，**8 个用例**：

```
✅ base64 PNG：字节逐一对得上
✅ MIME 类型被正确取出
✅ ★ 0x80 以上的字节不会被截断（charCodeAt 经典坑）
✅ 非 base64 的 dataURL 当文本处理
✅ 空的 base64 不会炸
✅ 没有逗号的畸形输入不会炸
✅ 256KB 数据正确往返（抽查首尾和中间）
✅ 确认现在是真图：真 PNG 文件能解出正确的文件头
```

测试是**从 `.tsx` 源码里把函数抠出来**执行的（用 esbuild 剥掉类型标注），
不是抄一份 —— 抄一份的话改了源码测试还是绿的，等于没测。

## 0.21.0

### ① 修复：「退出投屏」之后声音还在响

**现象**：点了「退出投屏」，画面没了，**但共享的声音照旧在放**。

**根因**：画面和声音是**两条完全独立的通道**，而之前的代码只管了画面：

```tsx
// 之前 —— 声音和"看不看"毫无关系
{screenAudio.map(({ track }) => (
  <VideoTile track={track} muted={voice.deafened || screenVolume === 0} />
))}
```

退出投屏只是把**视频**那个组件卸载了（于是 LiveKit 停止订阅、省下 8 Mbps），
而音频元素还挂在那儿，音量也还是原来那个。

**顺带还发现一个更早就存在的毛病**：两个人同时共享时，
**两路共享声音会同时播出来** —— 因为你根本没选要看哪一路，但两路都在响。

#### 修法：声音跟着「正在看的那一路」走

```ts
const screenAudioVolume = (key: string): number => {
  if (voice.deafened) return 0
  if (!watching || watchingShare?.key !== key) return 0   // ← 关键
  return screenVolume
}
```

- **没在看** → 静音
- **看的是别人那一路** → 自己那一路静音（真的不会两路同时响了）
- 关喇叭 → 全部归零

> **只是静音，没有退订。** 共享声音只有 64 kbps，
> 退订再重订会带来重新协商的延迟，不值当。
> 真正省流量的是**画面**那条（8 Mbps），那条确实断开了。

#### 埋了一个坑，顺手拆了

画面和声音要靠一个 key 对上，**两边必须用同一个函数算**。
之前两边写的是不同的表达式（`voiceKey(p)` vs `p.attributes?.userId || p.identity`），
现在统一成 `voiceKey`。

为此把 `voiceKey` 的参数类型从 `VoiceMember` 放宽成**结构类型** ——
LiveKit 的 `Participant` 也要用它，而 `Participant.name` 是可选的，
套不进 `VoiceMember`。

### ② 全屏看投屏时，控制条自动隐藏

**之前**：全屏之后屏幕顶上**永远杵着一条工具栏** ——
而那块区域通常正是画面内容所在的地方，很碍事。

**现在**：**鼠标移到屏幕上方**才出来，移开就滑走。

```
进入全屏      → 控制条先亮 2.5 秒（否则用户不知道顶部有这些东西）
鼠标停在别处  → 控制条藏着；闲置 2.5 秒后**光标也消失**
移到屏幕上方  → 控制条滑出来
移开          → 滑回去
退出全屏      → 常驻显示（窗口模式下藏起来没道理）
```

#### 中途改过一次：从「一动就出来」改成「移到顶部才出来」

第一版做的是"鼠标一动就出来"。**太吵了** —— 全屏看别人操作或者看视频时，
鼠标稍微碰一下桌面，顶上就滑下来一条，很跳。所以改成了"移到顶部才出"。

#### ⚠️ 关键：「光标」和「控制条」是**两件独立的事**

判断条件**故意不一样**：

| | 什么时候藏 | 什么时候回来 |
|---|---|---|
| **光标** | 鼠标闲置 2.5 秒 | **鼠标一动就回来** |
| **控制条** | 鼠标离开顶部区域 | **只有移到顶部才出来** |

光标必须"一动就回来"——**不然它藏起来之后你根本找不到自己在哪，
也就谈不上"把鼠标移到顶部"了。** 这两件事混成一个条件就废了。

（鼠标正停在顶部时也不藏光标 —— 你正要操作控制条。）

#### 迟滞：两个阈值，避免在边界上反复横跳

```
显示用 90px，隐藏用 130px
```

用同一个值的话，鼠标停在边界上轻微抖动会让控制条**一闪一闪**。
这和 CSS 里 `:hover` 加过渡要配 `pointer-events` 是同一类问题。

<details>
<summary>还有两个不做就会出问题的细节</summary>

#### 一个不做就会留黑边的细节

控制条**必须是绝对定位浮在画面上**，而不是占一行布局空间：

```
只做 translateY(-100%)     →  看不见了，但**那一行空间还在**
                              →  顶部留一条黑边，画面永远占不满
position: absolute + 浮层   →  画面真正占满整个高度      ✅
```

浮层用半透明 + `backdrop-filter` 模糊 —— 既看得清按钮，也不至于把画面挡死。

#### 藏起来之后必须 `pointer-events: none`

否则它会挡住鼠标事件，**移到顶部反而触发不了"唤醒"**。

## 0.20.0

这一版改了三块：**提示音**、**投屏的观看方式**、**不在频道时的显示**。

### ① 开关麦的提示音 —— 真正的问题是**频率**，不是音量

**之前的毛病**：闭麦 300 Hz、开麦 880 Hz，只有 0.08~0.11 秒、峰值 0.13。
用户的原话是「**需要仔细去听才能听到**」。

**光把音量调大治标不治本** —— 这两个频率**都压在语音的能量区里**。
一边听别人说话一边按闭麦，那一声会被**掩蔽**掉，开多大声都没用
（开太大还吵）。

真正的修法是**换频段**：

```
人耳在 1~4 kHz 最敏感，而语音的能量到那个频段已经明显下降
```

所以两头都往上抬：

| | 之前 | 现在 |
|---|---|---|
| 闭麦 | 300 Hz | **880 Hz** · 0.16 秒 |
| 开麦 | 880 Hz | **1568 Hz** · 0.12 秒 |
| 峰值 | 0.13 | **0.30** |

两个音仍然差一个八度（低的是"关了"、高的是"开了"），方向感保留。

**顺手统一了另外两组的音量**，因为混着用不同音量只会让人以为哪个坏了：

| | 之前峰值 | 现在 |
|---|---|---|
| 开关喇叭（双音） | 0.14 | **0.30** |
| 进出频道（双音） | 0.16 | **0.24** |

麦和喇叭现在只差**形状**（单音 / 双音）和**音区**（高 / 低），不靠音量区分。

### ② 投屏改成「**点击才看**」

**之前**：一有人共享屏幕就**自动占掉整个上半屏**，而且不管你感不感兴趣，
客户端都会去订阅那一路视频。

**现在**：只在原画面位置出一个显眼的按钮 ——

```
🖥  小明 正在共享屏幕            [ 点击观看 ]
```

点一下才打开画面。画面头部多了一个 **「退出投屏」** 按钮，点了就回到按钮状态。

**这不只是界面偏好，还是省流量**：

```
不订阅 → LiveKit 的 dynacast 会让分享者**停止发那一路**
       → 服务器出口直接掉到 0
```

1080p60 是 8 Mbps，**一个小时 3.6 GB** —— 大多数时候大家只是聊天，
根本没人看画面，那份流量现在不用花了。

**两个按钮的区别**（故意分开的）：

| 按钮 | 作用 |
|---|---|
| **收起** | 画面藏起来、聊天区变大，但**还在接收**画面 |
| **退出投屏** | **真的断开**，分享者那边也会跟着停发 |

> 收起之后那条细条上也放了一个「退出投屏」——
> 不然那个按钮跟着头部一起藏起来了，想不看得先展开，多一步。

**自己刚开的共享会自动打开画面** —— 不然你会盯着一个"点击观看"的按钮想
"到底共享成功了没有"。而且会**指定看自己那一路**，
两个人同时共享时不会给你显示别人那个。

### ③ 投屏按语音频道隔离

**要求**：不在某个语音频道里，就不该看到那个频道的投屏。
频道 1 和频道 2 都有人在共享时，我在频道 1 就只能看到频道 1 的。

#### 先澄清一件事：视频**本来就是隔离的**

这不是靠过滤做到的，而是**架构决定的** —— 每个语音频道是一个**独立的 LiveKit 房间**：

```
App.tsx        voice.connect(cfg, c.id)        ← 房间名 = 频道 id
     ↓
服务端          createAccessToken({ room })     ← 一个频道一个房间
     ↓
App.tsx        participants = [自己, ...voice.room.remoteParticipants]
                                        ↑ 只包含**我这个房间**里的人
     ↓
App.tsx        screenShares 从 participants 里筛
```

所以在频道 1 时，频道 2 的轨道**物理上不在我这边** —— 拿不到，不用过滤。

#### 真正的问题是**断线时没清房间状态**

`useVoiceRoom` 里主动退出（`disconnect()`）会清掉 `room`，
但**掉线走的是另一个分支**（`onDisconnected`），那里只改了 `status`，
`room` 还留着 —— 于是界面停在上一个房间的样子：
成员列表、**投屏画面**都还挂着，但那些轨道早就死了。

**看起来就像"我明明不在频道里，怎么还显示着投屏"。**

修了两处：

1. **`onDisconnected` 里也把房间状态清干净** —— 掉线、服务端重启、
   网络抖动，都会正确地回到"不在频道里"
2. 投屏的整套界面（邀请按钮 + 画面）以 **`inVoice`** 为前提，
   人不在频道里时什么都不显示

#### 顺带：主动退出 / 换频道不再弹错误

`Disconnected` 事件在「自己点退出」「换频道」「掉线」三种情况下**都会触发**，
但含义完全不同。之前前两种也会弹一个红色的「连接已断开」——
那是把正常操作当成故障了。

现在用**时间戳**记"我们刚主动断开过"，而不是布尔标志：

```ts
expectedDisconnectAtRef.current = Date.now()   // 断开前先记一笔
...
const expected = Date.now() - expectedDisconnectAtRef.current < 3000
```

为什么是时间戳：**布尔标志挡不住异步到达的事件** ——
`await room.disconnect()` 返回时标志早就复位了，事件才慢悠悠地到。
时间戳不管事件什么时候来都认得出。

（换频道那条路径也补上了 —— 它是 `connect()` 里主动断开旧房间的，
之前也没标记。）

## 0.19.1

### 修复：不在频道里也会听到别人进出的提示音

**之前**：只要客户端开着，**任何**语音频道有人进出都会"叮"一声。
人在大厅坐着看文字频道，或者根本没进语音，也会被别的频道的进进出出一直打扰。

**现在**：只有**自己所在那个频道**的进出才响。

| 情况 | 之前 | 现在 |
|---|---|---|
| 别人进出**我所在的**频道 | 🔔 响 | 🔔 响 |
| 别人进出**别的**频道 | 🔔 响 | 🔕 不响 |
| 我没进任何语音频道 | 🔔 响 | 🔕 不响 |
| 我自己进频道 | 🔔 响 | 🔔 响 |
| 我自己退频道 | 🔔 响 | 🔔 响（本地放，见下） |

---

#### 为什么过滤放在客户端，而不是服务端

服务端**是故意广播给所有人的** —— 它靠每 3 秒一轮的轮询才知道谁在哪个房间，
让它精准投递的话提示音最多会慢 3 秒，而"叮"一声要的就是即时。

而「**我在不在这个频道**」这件事，客户端自己最清楚。所以：

```
客户端上报进出（即时）
   → 服务端广播给所有人（快，不用查谁在哪）
      → 每个客户端自己判断"这个房间是不是我所在的"（准）
```

#### 顺带补了一个漏掉的字段

`api.ts` 解析 `chime` 消息时**只取了 kind 和 name，把 room 丢了** ——
所以客户端根本没机会做这个判断。现在把它带出来了。

#### 一个细节：自己退出的那一声改成**本地直接放**

广播回来的时候，我已经不在那个房间了，会被新的过滤挡掉。
但「我退出了频道」这件事本身该有个即时反馈，所以那一声改成本地放。

**不会和广播重复** —— 那一条正好被过滤掉了。

（自己**进入**频道不用特殊处理：广播到达时我确实在那个房间里，过滤会放行。）

#### 还修了一个隐藏的坑

WS 回调只在**建立连接时创建一次**，所以它闭包里捕获的 `voiceJoinedRoomId`
永远是连接那一刻的值（`null`）。直接用它做判断的话，过滤会把**所有**提示音
都挡掉 —— 变成"彻底没声音"，比现在还糟。

所以用了一个 ref 存"我现在在哪"，并且在发广播**之前**就同步好。

---

### 同时要更新的服务端（本次一起发布）

客户端这次上报得靠服务端配合，所以**服务端也要重新部署**。

之前有个缺口：**直接关掉客户端、或者强杀进程 / 断网**，频道里的人
**听不到那一声"离开"** —— 因为提示音完全靠客户端主动上报，
而那些情况下客户端根本没机会上报（关窗口时 React 是**卸载**，
那个依赖房间变化的 effect 不会触发）。

现在服务端在**每 3 秒的轮询**里顺手对比两轮快照，发现有人消失就补一声。

| 情况 | 之前 | 现在 |
|---|---|---|
| 点「退出语音」 | 🔔 即时 | 🔔 即时（客户端上报） |
| **直接关客户端** | 🔕 不响 | 🔔 **最多慢 3 秒** |
| 强杀 / 断网 / 断电 | 🔕 不响 | 🔔 最多慢 3 秒 |

**去重**：正常退出时客户端报一次、轮询 3 秒后又看到一次 ——
不去重会响两声。所以按 `房间\|userId` 记"刚刚报过"的标记，
轮询撞上就跳过（窗口 12 秒）。**重新加入时会清掉标记**，
否则"报过离开 → 又进来 → 被强杀"会被旧标记误吞、永远不响。

**防幻听**：LiveKit 整体重启时会返回空列表，那不是"所有人同时退出"，
所以快照整体变空时一条都不发。

新增文件 `src/voice-chime.js`（纯逻辑、broadcast 是注入的）+
`test-chime-diff.mjs`（**19 个用例**，含上面几条关键回归）。

## 0.19.0

### 新增：关喇叭 / 开喇叭也有音效了

和开关麦一样，**点和快捷键都会响**，而且**只有自己听得见**。

---

#### 音色怎么设计的

麦克风本身已经有音效了，喇叭不能做成一样的 —— **不然闭麦和关喇叭听起来一模一样，
不看屏幕根本分不清自己关掉的是哪一个。**

所以靠**单音 / 双音**区分：

| 动作 | 音型 | 听感 |
|---|---|---|
| 闭麦 | **单音** 300 Hz，0.11 秒 | 短促的"咚" |
| 开麦 | **单音** 880 Hz，0.08 秒 | 短促的"哒" |
| 关喇叭 | **双音下行** 494 → 330 Hz | 像"合上" |
| 开喇叭 | **双音上行** 330 → 494 Hz | 像"打开" |

设计意图：

> **麦克风是小的东西**（一个短促单音），
> **喇叭是大的东西**（两个音、落得更低）。

单音 vs 双音的差别，比"两个不同的音高"可靠得多 ——
尤其在游戏里、背景音很吵的时候，音高差往往听不出来，但"响一下"和"响两下"
一耳朵就分得清。

#### 两条路统一走同一个函数

```ts
// 快捷键
shortcutHandlerRef.current = (action) => {
  if (action === 'mute') toggleMicWithSound()
  else toggleDeafenWithSound()      // ← 和点按钮完全一样
}

// 按钮
onClick={toggleDeafenWithSound}
```

**音效按"即将变成什么状态"来选、而且是先出声再切** ——
这样即使切换失败，音效也和用户按下时看到的状态一致。

#### 一个细节：关喇叭会顺带闭麦，但**不再放闭麦音**

Discord 的规矩是关喇叭时连麦克风一起关（`useVoiceRoom.toggleDeafen` 干的）。
但这里**故意不**放闭麦音 —— 两个音叠在一起只会糊成一团。
喇叭自己的双音已经说明"整个都不出声了"。

#### 顺带修掉一个小毛病

不在语音频道里按这两个快捷键，之前会**响一声但什么都不发生**。
这比没声音更让人困惑。现在没有 room 就直接返回，**连音效也不放**
（按钮上本来就有 `disabled`，快捷键这条路上得自己挡）。

## 0.18.1

### 修复：所有人都像"在浴室里说话"

**先说结论：这不是音质问题。** 码率、编码、采样率都没变，也没坏。
是客户端**把同一条音轨播了两遍**。

---

#### 现象

频道里每个人的声音都带一层很短的"回声"，像是浴室或空房间里说话。
不是对方麦克风的问题 —— **所有人听起来都这样**，而且自己录一段再听也这样。

#### 根因

我们为了做「**音量可以超过 100%**」用了 Web Audio 增益
（`HTMLMediaElement.volume` 规范上封顶 1，只有 Web Audio 的 GainNode 能放大）。

LiveKit 的 `RemoteAudioTrack` 有两条路：

```
attach(element)          接 Web Audio 时**会**把元素静音：
                             element.volume = 0
                             element.muted = true

setAudioContext(ctx)     接 Web Audio 时**不会**静音 —— 只连音频图
```

**而我们的调用顺序恰恰是最坏的那种**：

```
① UI 渲染 → track.attach(el)        → 元素开始播放
② 音量 effect → setAudioContext(ctx) → Web Audio 也开始播放
③ setVolume(1.0)                    → Web Audio 模式下**只动 gainNode**，
                                       根本不碰元素音量（见 SDK 源码）
```

结果：**同一条音轨走了两条路径同时出声**。

```
元素直出      ──────────────▶ 声卡
Web Audio     ────(缓冲)─────▶ 声卡      ← 多绕了一层，晚 10~20ms
```

两个**延迟不同**的相同信号叠加 = **梳状滤波** —— 频响上出现一排等间距的
凹陷，听感就是"空、闷、像在浴室里"。

#### 为什么之前没发现

这段代码从「音量增益」那个版本就在了，但它只在**真的设过音量**时才生效？
—— 不是。它是**无条件**给每条远端音轨接 Web Audio 的，
所以理论上**从那时起就一直有**。只是它很轻微，而且我们一直没把
"声音有点怪"和"音量功能"联系到一起。

> 这也解释了一个细节：`setVolume()` 在 Web Audio 模式下只动 gainNode，
> 所以元素那个"多出来的 100% 音量"**永远不会被纠正**，会一直存在。

#### 修法

```ts
// 设完 AudioContext 后，自己把已挂上的元素静音
if (webAudioLive.has(track)) {
  for (const el of track.attachedElements ?? []) {
    el.volume = 0
    el.muted = true
  }
}
```

（新挂上的元素不用管 —— 那时 `audioContext` 已经有了，
`attach()` 自己会走进静音那段分支。）

#### 顺带的一个改进

改成**只在真的需要超过 100% 时才走 Web Audio**：

| 音量 | 走哪条路 | 为什么 |
|---|---|---|
| ≤ 100% | 元素直接播放 | 延迟最低，也不会遇到 AudioContext 被自动播放策略挂起（那会直接**没声音**） |
| > 100% | Web Audio 增益 | 唯一能放大的办法 |

接过之后就不再拆 —— 反复重建音频图会在拖动滑块时爆音。

---

#### 记一笔教训

**用 SDK 的 `@internal @experimental` 接口，一定要去读它隔壁那些"正常"方法的实现。**

我当初看到 `setAudioContext` 就假设"接了 Web Audio，元素就被绕过了"——
`attach()` 里确实有那么两行静音代码，看着就像这个假设是对的。
但 `setAudioContext()` 里**没有**，而我根本没去读它。

一个 `console.log(track.attachedElements[0].muted)` 就能发现的 bug，
藏了好几个版本。

## 0.18.0

### 新功能：投屏的系统声音**不再包含通话声**

这是拖了很久的一个问题，终于根治了。

**之前的情况**：勾上「同时共享系统声音」后，对方会听到自己刚才说的话，晚一点点回过来。
我一度说"戴耳机就好"—— **那句是错的**（0.17.3 已更正）。WASAPI 回环录的是
**输出设备的数字流**，跟声音有没有从喇叭出来无关，耳机和音箱是同一路。
通话声必然在里面，因为这个声音就是从你的系统输出播出来的。

**现在**：用 Windows 的**进程级回环捕获**，做的是减法：

```
系统混音（游戏 + 音乐 + 通话声）
  −  本软件的进程树（通话声就是从这儿放出来的）
  ─────────────────────────────────
  =  游戏 + 音乐
```

**通话声是物理上没进过采集链路**，不是事后过滤 —— **零音质损失**。

---

### 怎么做到的

新增一个 Windows 原生插件（`native/process-loopback/`），用
`PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE` 捕获整系统声音、
但排除本软件的进程树。

**关键点**：Chromium 的音频不是渲染进程播的，而是一个独立的 utility 进程：

```
Electron 主进程  ← 排除这棵树
   ├── 渲染进程
   ├── GPU 进程
   └── 🎵 AudioService 进程   ← 通话声其实是从这里出去的
```

排除**主进程**才能把这棵树整个排掉。用渲染进程自己的 pid 不行 ——
它和 AudioService 是**兄弟**，不是父子。

**数据路径**（`src/renderer/src/lib/screenAudio.ts`）：

```
原生插件 (16位PCM/48kHz/立体声)
  → preload（直接加载插件，**一次 IPC 都不走**）
     → new AudioData({ format: 's16' })    ← 零格式转换
        → MediaStreamTrackGenerator.writable
           → MediaStreamTrack → LiveKit 发布
```

`AudioData` 原生支持 `s16`，正好是插件的输出格式，
所以中间**不需要 AudioWorklet、不需要环形缓冲、不需要重采样**。

---

### 为什么放在 preload 而不是主进程

渲染进程开了 `sandbox: false`，preload 有完整 Node 能力。在那里直接
`require` 原生插件，采集线程的回调就直接进渲染进程。

走主进程的话每秒要搬 200 条 IPC 消息，白白多一层拷贝和序列化。

---

### 用了 N-API，所以升级 Electron 不用重编

插件用的是 **N-API**（`node-addon-api`）而不是老的 NAN。
N-API 的 ABI **跨 Node 和 Electron 版本都稳定**。实测：

```
编译时   Node 24.16.0        modules ABI 137   napi 10
运行时   Electron 33.4.11    modules ABI 130   napi 9
         → require ✅  实例化 ✅  stop() ✅
```

主版本不同、原生 ABI 号也不同，**同一个 `.node` 照常工作**。
这把原生模块最大的那条维护成本消掉了。

---

### 降级是安全的

插件拿不到时（非 Windows、没编译、Windows 版本 < Build 20348）
**自动退回 Chromium 的整系统捕获** —— 功能降级，而不是共享失败。

选择器里的提示会相应变化：

| 情况 | 提示 |
|---|---|
| 插件可用 | ✅ 这一路系统声音**不含通话声** |
| 插件不可用 | ⚠️ 会包含通话声 + **具体原因** |

**朋友拿到安装包什么都不用装** —— 原生模块的编译只发生在发布这台机器上。

---

### 验证方式（不靠耳朵，看频谱）

用两个互不成谐波的纯音做**双向对照**，环境噪声会被完全抵消：

```
方向 A  --include（只录 Electron）
  1500Hz  +143.3 dB [有]  /  440Hz  +16.6 dB [无]    ✅

方向 B  --exclude（系统声音 − Electron）
   440Hz  +133.0 dB [有]  /  1500Hz  +17.8 dB [无]    ✅
```

**同一测量、只改一个开关：1500Hz 掉了 126 dB。**

还有一条**最关键的** —— 真实场景是「**自己播声音、同时排除自己**」：

```
本进程自己播 1500Hz（模拟通话声）+ 外面播 440Hz（模拟游戏声）
排除本进程主进程 PID 采集

   440Hz  +132.7 dB [有]    1500Hz  +19.8 dB [无]     ✅
```

采集方自己就在被排除的树里，照样能采到别的声音、同时把自己排除掉。

> 顺带一个教训：**别拿"收到多少数据"当成功判据**。
> 第一次跑测试时收到 198 块、完整度 99%，看着完全正常，
> 但峰值只有 11/32767，也就是**静音**。链路通 ≠ 采到了东西。

### 踩过的坑

| 坑 | 原因 |
|---|---|
| `.cpp` 没加 BOM → 一堆莫名语法错误 | MSVC 按系统 GBK 读 UTF-8 源码，中文注释变乱码把语法搞崩 |

| Node 头文件下不动 | nodejs.org 连不上 → `--dist-url=https://npmmirror.com/mirrors/node` |
| `ELECTRON_RUN_AS_NODE=1` | 这台机器上设着这个变量，Electron 会退化成普通 Node |

## 0.17.3

### 更正：之前那句「戴耳机就好」是错的

从 0.4.0 起，共享屏幕时开着系统声音会显示这段提示：

> ⚠️ 如果你用音箱外放而不是耳机，对方会从你的共享声音里听到他们自己的回音，
> 因为系统声音捕获会把音箱里放出来的语音也录进去。要么戴上耳机……

**这是错的。耳机解决不了这个问题。**

**为什么**：WASAPI 回环捕获录的是**输出设备的数字流**，
跟声音有没有真的从喇叭里发出来**毫无关系**：

```
通话声音 → 系统混音器 → 输出设备（耳机 / 音箱，同一路数字流）
                             ↓
                      WASAPI 回环在这里复制一份
```

耳机能防的是**麦克风收到喇叭的声学回声**（那确实只有外放才会发生），
**防不了回环捕获** —— 我把这两个完全不同的问题当成一回事了。

**真实情况**：捕获到的 = 你输出设备正在播放的一切
= 游戏声 + 音乐 + **通话里所有人的说话声**。

因为通话声**就是从你的系统输出播出来的**，它必然在捕获内容里。

> 所以「共享系统声音」和「不让对方听到自己」，
> **在这个架构下无法同时成立** —— 唯一的真正解法是
> **只录指定程序的音频**（Windows 进程级回环），
> 但那要绕开 Chromium 的采集实现自己用 C++ 采，是几天的工作量，而且仅限 Windows。

**现在的提示改成实话了**，不再让人误以为戴个耳机就没事。
观看端仍然可以调小「共享声音」的音量来缓解。

## 0.17.2

### 修复：提示条变成「纯红色块，没有文字」

根因是**通用类名撞车** —— 这个项目第二次栽在同一件事上
（第一次是右键菜单里的"红底红字"）。

```tsx
<div className={`toast ${notice.kind}`}>   // kind 是 'error' | 'info'
```

于是错误提示的类名是 `toast error`，而全局有一条：

```css
.error { color: var(--err); }
```

`background: var(--err)`（红底）+ `color: var(--err)`（红字）= **什么都看不见**。

**为什么之前没暴露**：`.toast` 和 `.error` 特异性都是 `(0,1,0)`，
只能靠"谁写在后面"分胜负。而我在 0.7.0 加附件样式时**又写了一遍 `.error`**，
它落在了 `.toast` **后面** —— 从那一刻起这个 bug 就存在了。

**修法**：类名加前缀，改成 `toast-error` / `toast-info`，并删掉那份重复的 `.error`。

### 调整：放宽快捷键的限制

之前一刀切要求"所有键都必须带 Ctrl / Alt / Shift"（功能键除外）。
这条定得**太严了** —— 很多语音软件的习惯用法就是单独一个 PageUp，
而 PageUp 根本打不出字，绑它并不影响输入。

现在按**是不是打字键**来区分：

| 键 | 能不能单独绑 | 为什么 |
|---|---|---|
| 字母、数字、空格、Tab、回车、退格 | ❌ **必须带修饰键** | 这些单独绑会让**所有程序里都打不出字** |

| 方向键 / Esc | ✅ 可以 | 同上 |

**代价是那个键不会再传给别的程序** —— 全局快捷键是系统级拦截，
这一点在设置界面里写明了。

> 保留的那条硬限制只有一处：字母和数字。那是唯一会"把键盘废掉"的情况，

## 0.17.0

### 新增：提示音

四个音，**全部用 Web Audio 现场合成**，不打包任何音频文件
（四个音加起来不到 70 行，比四个 .wav 还小，改起来也不用重新找素材）：

| 时机 | 音效 | 谁听得见 |
|---|---|---|
| 有人**加入**语音频道 | 两音**上行**（C5 → E5） | **所有人** |
| 有人**离开**语音频道 | 两音**下行**（E5 → C5） | **所有人** |
| **开麦** | 短促**高**音 | 只有自己 |
| **闭麦** | 短促**低**音 | 只有自己 |

上行/下行区分进出，音高区分开麦闭麦 —— 不用记音色也分得出来。

**为什么进出频道要所有人听得见，却不走麦克风**：
如果从进频道那个人的麦克风传出去，他一闭麦别人就听不到了。
所以客户端上报给服务端，服务端**广播一个事件**，每台客户端各自本地播放。
声音是真的"响在每个人机器上"，和麦克风状态完全无关。

**为什么由客户端上报而不是服务端自己判断**：服务端每 3 秒才轮询一次
LiveKit，靠它触发的话提示音最多慢 3 秒 —— 而"叮"一声要的就是即时。

### 新增：全局快捷键

设置 → 快捷键：

```
一键闭麦 / 开麦            [ Ctrl + Shift + M ]  [×]
一键闭音响 / 开音响        [ Ctrl + Shift + D ]  [×]
```

- **全局**快捷键 —— 窗口最小化、藏在托盘里、**甚至在游戏里都能按**
- 点按钮进入录制状态，按下什么就绑什么，不用手写 `Control+Shift+M`
- 默认沿用 Discord 的习惯用法（Ctrl+Shift+M / Ctrl+Shift+D）
- 走的是**和点按钮完全一样**的路径，所以音效和状态同步都一致

**三条防护：**

1. **必须带修饰键**（Ctrl / Alt / Shift），功能键 F1~F24 除外。
   全局快捷键是**系统级**的 —— 绑一个裸字母 `M` 会让所有程序里都打不出 m。

2. 被别的程序占用时**明确告诉用户**（"这个组合被别的程序占用了，换一个"）——
   否则他按下去没反应，只会以为程序坏了。
3. 退出时 `unregisterAll()`，不给系统留下幽灵绑定 ——

### 实现要点

- 录制快捷键的 keydown 监听挂在 **document 的捕获阶段**：
  要抢在别的监听之前拿到事件并 `stopPropagation`，
  否则按 Esc 想取消录制，结果把整个设置弹窗也关了。
- 快捷键的处理函数用 ref 转一手：`voice` 每次渲染都是新对象，
  直接放进订阅 effect 的依赖里会导致监听**每渲染一次就重挂一次**。
- 后端新增 `voiceChime` 消息：只负责把"有人进出频道"广播给所有人。

## 0.14.1

### 修复：双击图标会启动第二个实例，并**凭空多出一个用户**

这个 bug 比表面严重 —— 它丢的是**身份**。

**根因**：两个进程共用同一个 `userData` 目录，而 Chromium 的 localStorage
底层是 **LevelDB，同一时刻只允许一个进程打开**。

```
第二个进程读不到 localStorage
   → loadConfig() 拿到空值
      → ensureIdentity() 生成一个全新的 userId
         → 服务端凭空多出一个"新用户"
```

**更糟的是**：`OWNER_NAME` 是按**昵称**认人的，
所以这个新身份还顺手**把频道主抢了过去** —— 原来那个身份被降成管理员。

**修法**：加 `app.requestSingleInstanceLock()`。

- 拿不到锁的第二个进程**直接退出**，什么都不建。
  （`whenReady` 里也加了判断，免得它闪出一个窗口再消失，更难理解）
- 已在运行的那个实例收到 `second-instance` 事件，负责**把窗口唤到前面**
  —— 从托盘藏起来的话，这一步会把它重新显示出来
- 同时给界面推一条提示：**「Voice 已经在运行了，已经帮你切回这个窗口」**。
  没有这句的话，用户双击后什么都没发生，只会以为程序没启动，接着再点几次

### 顺带

- **提示条分了两种颜色。** 之前只有一种红色，于是「已上传 xxx」也显示成红的，
  看着像出错。现在 `info` 蓝色、`error` 红色，
  并且 **info 提示 4 秒后自动消失**（error 留着，让用户有机会看清）。

## 0.13.0

### 新增

- **音量增益到 200%。** 右键菜单里的滑块从 0~100% 扩到 **0~200%** ——
  100% 以上是**增益**，给麦克风特别小的人用。超过 100% 时标记会写成
  `150%（增益）`，一眼能看出这不是正常音量。

- **设置里新增「麦克风」一节 —— 降噪开关。**

  用的是**浏览器内置**的降噪：免费、零下载、几乎不占 CPU。
  如果别人说你声音**发闷、像隔了层布**，就关掉试试 ——
  内置降噪会把稳态噪音和人声一起削，有些人声被削得比较明显。
  回声消除和自动增益也是内置的，一直开着，没做成开关（关掉只会更差）。

### 实现要点

- **增益必须走 Web Audio。** `HTMLMediaElement.volume` 规范上**封顶 1**，
  到不了 200%。LiveKit 的 `RemoteAudioTrack.setVolume()` 内部有两条路：

  | 情况 | 走哪条 | 能超过 100% 吗 |
  |---|---|---|
  | 设过 `AudioContext` | `source → GainNode → destination` | **能** |
  | 没设 | 直接写 `el.volume` | 不能（封顶 1） |

  所以必须先 `setAudioContext()` 再 `setVolume()`。两个坑：

  1. **必须共用一个 `AudioContext`** —— Chromium 对每个页面能创建的数量有硬限制
     （约 6 个）。每人一个的话，人一多后面的就创建失败，**直接没声音**
  2. 一旦走了 Web Audio，**元素自身的 `muted` / `volume` 会被绕过** ——
     所以静音也必须靠 `setVolume(0)`，不能只靠 `<video muted>`
     （两边都设着，是为了 Web Audio 用不上时还能静音）

  `setAudioContext` 在 SDK 里标着 `@internal @experimental`，所以做了三层防护：
  运行时检查它存不存在、每条轨道只设一次、将来 SDK 去掉它也只是退回
  **"不能增益"而不会没声音**。

- **降噪开关改完要重新采集。** 浏览器只在 `getUserMedia` 那一刻读这些约束，
  所以切换时先关麦再开麦，让它重新协商。

### 修复：类型检查从项目一开始就是坏的

`npm run typecheck` 里躺着 **24 个错误**，一直没人发现。原因是
`src/preload/index.d.ts` —— 那个声明 `window.desktop` 的文件 —— **从来没被包含进来**：

- 它和 `index.ts` **同名**，TypeScript 会把同名的 `.d.ts` 当成 `.ts` 的编译产物**排除掉**
- `tsconfig.json` 的 `include` 里也没有 `*.d.ts`

改名成 `global.d.ts`，并在 include 里加上 `src/**/*.d.ts` 之后，**错误清零**。

> 之所以一直没暴露：构建走的是 esbuild，它只**剥掉**类型、不做检查。

## 0.10.1

### 修复

- **右键菜单里的「删除频道」是纯红色一块、看不见文字**，鼠标移上去才露出来。

  不是颜色选错了，是 **CSS 特异性打架**：

  | 规则 | 特异性 | 效果 |
  |---|---|---|
  | `button.danger { background: var(--err) }` | `(0,1,1)` | 红底 |
  | `.context-menu-item { background: transparent }` | `(0,1,0)` | **输给上面那条** |
  | `.context-menu-item.danger { color: var(--err) }` | `(0,2,0)` | 红字 |

  `button.danger` 虽然只有一个类，但**多了一个元素选择器**（`button`），
  在"元素个数"这一维度上压过了 `.context-menu-item` ——
  于是背景是红的、文字也是红的，**红底红字 = 完全看不见**。
  鼠标移上去时 `.danger:hover` 把文字改成白色，字才浮出来。

  修法：给 `.context-menu-item.danger` 补上 `background: transparent`，
  特异性变成 `(0,2,0)`，两个维度都赢过 `button.danger`。

  > 教训：全局的 `button.xxx` 规则比想象中更容易"穿透"进组件里。
  > 元素选择器会给特异性白送一分，写组件级样式时最容易忽略这一点。

- 截图**复用附件上传的全套路径**（大小限制、身份校验、广播都一样），

  | 共享声音 | Opus @ 48 kHz · 立体声 · 最高 64 kbps（`musicStereo` 档） |
  | 回声消除 | 系统内置 AEC + 降噪 + 自动增益 |

  **音频档位现在是显式指定的**（`MIC_AUDIO_PRESET` / `SCREEN_AUDIO_PRESET`），
  不再吃 LiveKit 的默认值 —— 这样"现在是什么音质"有确定答案，
  界面显示的数字也直接取自配置对象，不会跟实际脱节。

  选 24 kbps 单声道是因为**服务器按流量计费**：说话用 24 kbps 完全够，
  而 320 kbps 立体声是它的 13 倍。

## 0.4.0

### 修复

- **两个人同时共享屏幕时只能看到自己的画面。**
  找共享流的循环写成了"找到第一个就 `return`"，而参与者列表的**第一个永远是本地参与者** ——
  所以只要自己在共享，别人的画面就永远轮不到。
  现在会把所有共享流都收集起来，用标签页切换；默认优先显示**别人的**画面
  （自己的画面自己心里有数，不用占着主画面）。

### 新增

- **多路共享切换**：画面标题栏出现标签页，点一下换一路；多于一路时显示「共 N 路」。
  收起状态下也会提示「还有 N 路」。
- **每次共享单独决定要不要系统声音**：选择器顶部加了勾选框，
  不再统一用设置里的默认值 —— 有时候要连游戏声一起给，有时候只想给人看代码。
- **观看者可以单独调共享声音的音量**：画面标题栏里有个独立滑块，
  和麦克风音量完全分开。对方外放导致你听到自己回音时，把它拉小就行，不用整个静音。
  音量会记住，下次打开还是这个值。

### 其他

- `npm run publish:update` 现在**只上传当前版本**的产物。
  之前用的是 `*.exe` 通配，`release\` 目录里堆的历史版本每次都会被重传一遍（几百 MB）。
  还会校验 `latest.yml` 里的版本号和 `package.json` 是否一致，不一致直接中止 ——
  防止 "dist 之后又改了版本号" 导致把错误版本的清单推给所有人。

### 关于「看别人共享时听到自己的回音」

这不是 bug，是**系统声音捕获的固有行为**：

```
A 用音箱外放
   → B 的声音从 A 的音箱里放出来
      → A 的"系统声音"捕获把这个声音也录进去了
         → 传给 B
            → B 听到自己的声音
```

唯一的根治办法是**戴耳机**。所以现在：
- 勾选共享系统声音时会显示明确警告
- 观看端有独立音量，实在吵就拉小

### 说明：这一版同时用来验证自动更新链路

自动更新有个**引导问题**：第一个带这功能的版本，没法从"没有这功能"的版本升上来。

| 版本 | 有 `autoUpdater` 代码 | 有 `resources\app-update.yml` | 能检查更新吗 |
|---|---|---|---|
| 0.1.0 | ❌ | ❌ | **不能**（那时代码和配置都还没有） |
| 0.2.0 | ✅ | ✅ | 能 |
| 0.3.0 | ✅ | ✅ | 能 |

所以要验证自动更新，正确的做法是**装 0.2.0，然后发布 0.3.0**。

## 0.2.0

### 新增：自动更新

基于 `electron-updater` 的 **generic provider** —— 更新包放在**你自己的 ECS** 上，

- 启动 8 秒后自动检查一次，之后每 6 小时一次

- 下载完成后可以「立即重启安装」，也可以「退出时安装」

## 0.1.0

首个可日常使用的版本。

### 服务端（voice-server）

- **LiveKit SFU + Node 后端**，全部 systemd 托管，开机自启、崩溃自动重启
- **不需要域名、证书、备案**：原生客户端直连 `ws://IP:7880`；UDP 端口复用（7882-7885）让安全组只需 4 条规则
- **零原生依赖**：数据库用 Node 24 内置的 `node:sqlite`，不装 Postgres、不编译 C++ 模块
- 文字频道：消息持久化、按 `id < before` 翻页、支持多个频道
- 语音频道：Opus + DTX（静音不发包）+ RED（抗丢包）
- 1080p60 屏幕共享
- 角色系统：频道主 / 管理员 / 成员
- 成员表：昵称、头像、角色，按稳定 `userId` 记录
- `OWNER_NAME` 机制：频道主跟昵称绑定，清缓存/换电脑/重装都能自动拿回
- `scripts/admin.js`：服务端直接查改角色
- 每 3 秒轮询 LiveKit，把「每个语音频道里有谁、谁闭麦了、谁在共享」推给所有客户端

### 客户端（voice-client）

- Electron + React + TypeScript，Discord 式三栏布局
- **语音**：开麦 / 闭麦
- **关闭喇叭（deafen）**：按 Discord 的规矩 —— 关喇叭顺带闭麦，取消时恢复原先的麦克风状态
- **屏幕共享**：
  - 应用内缩略图选择器（整屏 / 单窗口）
  - 支持系统声音（Windows）
  - `contentHint = 'text'`，文字清晰度优先
  - 与聊天**上下分栏共存**，中间手柄可拖动调整，可一键收起
  - 全屏观看
- **文字频道**：实时消息 + 历史记录
- **角色系统**：频道主可任命/撤销管理员；管理员可增删频道、改服务器信息
- **服务器名字与头像**（全局共享，存在服务端）
- **个人头像**（10 底色 + 24 emoji）与昵称
- 稳定的本地身份（`userId` + `userKey`），角色不随重连丢失
- 屏幕共享画质档位：720p30 / 1080p30 / 1080p60 / 1080p60 高画质

### 已知限制

- 权限校验只到「连接级」：知道邀请码就能连，连上后只能操作自己的连接。
  几个朋友自用够用，**要对外开放必须换成真正的账号体系**。
- 服务端地址和邀请码内置在安装包里（设置里可改，但收在「高级」折叠区）。
  代价是拿到安装包的人都能接入。
- 历史消息保留发送时的昵称快照，改名不会改写旧消息。
- 语音频道里的人名/状态最多有 3 秒延迟（服务端轮询周期）。
