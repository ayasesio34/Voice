# Voice

自建的语音 + 文字 + 投屏客户端与服务端，为几个人的小圈子写的私服，类似自建 Discord。

## 关于这个项目

**代码和文档绝大部分由 AI（DeepSeek）生成**，人类负责提需求、定技术选型、实际部署和验收。

已经验证的：200 多条测试断言；真实部署在一台云服务器上，并有一小圈人在日常使用。
还没有做的：**没有专业安全审计**，没有大规模并发验证，客户端目前只在 Windows 上跑过。

自己几个人的小圈子用是够的。要对外提供服务，或者拿去做别的事，**请先自己审一遍代码**。

---

> 仓库里的服务器地址和邀请码都是**占位符**，部署时按下面的说明换成你自己的。

## 组成

| 目录 | 是什么 |
|---|---|
| `voice-server/` | 服务端：Node 22.5+ / Fastify 5 / `node:sqlite`（零原生依赖）/ LiveKit 单文件二进制（不用 Docker） |
| `voice-client/` | 桌面客户端：Electron 33 + React 19，目前以 Windows 为主，支持自动更新 |

## 功能

- **语音频道** —— 麦克风处理开关（降噪 / 回声消除 / 自动增益）、独立音量、进出铃声
- **文字频道和私聊** —— 附件、截图、云端文件、搜索
- **投屏** —— 720p30 到 2K60 共七档，含一档 2.5 Mbps 省流档；独立音量；显示观看者头像
- **状态** —— 「正在听」（Windows SMTC）和「正在玩」（进程检测 + 可共享的白名单）
- **界面** —— 深色 / 浅色主题、颜色加 emoji 的头像、表情选择、图片查看器
- **权限** —— 频道主 / 管理员 / 成员

## 几个设计取舍

- **服务端零原生依赖** —— 用 Node 22.5+ 自带的 `node:sqlite`，而不是 `better-sqlite3`。
  后者要下载预编译二进制，国内经常失败，部署会很脆。

- **身份由客户端生成，不由服务端下发** ——
  开发模式下 React StrictMode 会把 effect 跑两遍。如果身份由服务端下发，
  第一个连接生成的身份（以及它拿到的频道主角色）就永远回不来了。
  客户端自己生成就没有这个问题。

- **投屏的 `contentHint` 比码率更重要** ——
  屏幕内容以锐利文字为主，编码器需要优先保边缘。设置选错会让帧率一直被压，
  看起来就是「卡」，而 CPU 和内存都看不出异常。

- **仓库里有三条互相矛盾的编码规则** ——
  `.cmd` 必须纯 ASCII，`.ps1` 必须带 UTF-8 BOM，`.yaml` 绝不能有 BOM。
  写错任何一条都会以很难查的方式炸掉，所以仓库带了护栏脚本自动检查。

- **投屏分享的是游戏和音乐的声音，不含频道里的通话声** ——
  系统的桌面回环录的是默认输出设备上的一切，包括我们自己正在播的通话声，
  那样对方会听到自己的回声，根本不能用。所以这里用的是 Windows 的**进程级回环**：

  ```
  系统混音（游戏 + 音乐 + 通话声）
    −  本软件的进程树（通话声从这儿放出来）
    ─────────────────────────────────
    =  游戏 + 音乐
  ```

  通话声是物理上没进过采集链路，不是事后过滤，所以没有音质损失。
  这个能力目前只有 Windows 提供；在 Linux 上会退回整系统捕获，
  也就是投屏有画面、但没有声音，免得把通话声录进去。

## 部署到自己的服务器

1. 把 `voice-client/src/renderer/src/lib/config.ts` 里的 `YOUR_SERVER_IP`
   换成你的地址（两个端口也要按你的实际情况改）
2. 把 `voice-server/livekit/livekit.yaml` 的 `node_ip` 换成你的公网 IP
3. 按 `voice-server/开始操作.md` 走一遍
4. 自己设一个邀请码，填进 `.env`
